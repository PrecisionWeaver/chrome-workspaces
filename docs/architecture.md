# Architecture

A Chrome side-panel extension plus a local Node helper (macOS). Each workspace is a Chrome window, or a tab group inside a window, paired with a `claude` terminal. The helper owns every shell and the workspace list; the panel is only a view.

```
side panel (xterm.js) ──ws://127.0.0.1:4178──▶ helper ──▶ PTY: login shell → claude
service worker / panel ──/control (typed JSON)─▶ helper ──▶ ~/.chrome-workspaces/workspaces.json
local scripts ──HTTP + bearer token─▶ helper
claude (per workspace) ──hooks──▶ hooks/session-state.ts ──▶ ~/.chrome-workspaces/sessions/*.json, *.events.jsonl ──▶ helper
```

## Layout

Folders group code by what it is for, not by kind. Every module has its test beside it (`foo.ts`, `foo.test.ts`); the helpers that tests share live in `helper/testing/` and `extension/testing/`. There are no `index.ts` barrels: imports name the file. The entry points (`helper/src/main.ts`, `native-host.ts`; `extension/src/background.ts`, `panel.ts`, `popout.ts`) sit at the top of their root, because the LaunchAgent plist, the native-messaging manifest and the build name them by path.

## Things that are not obvious

- **Selection is per window**, stored in `chrome.storage`. Several workspaces can share a window (tab groups); the list is the selector. The list order is the one order shared by shortcuts, tab groups and the palette; an atomic `order` message keeps the list and Chrome's groups from ping-ponging.
- **Settings cards are dealt into columns by script.** `settings-layout.ts` picks one to three columns from the body's width and deals the cards out in turn (Usage and the workspace sessions first, setup and warnings across the top), because CSS columns cannot place a card and a grid leaves gaps under short ones. A card stays in the same column from one refresh to the next; a focused dropdown is left in place across a refresh.
- **Memory and CPU trends are sampled on a timer.** A snapshot is only taken while Settings is open, so `main.ts` calls `admin.sample()` every minute and `resource-history.ts` keeps the last 120 samples per running session (the shell tree's summed memory and CPU), dropping a session's history when it stops. They are lost when the helper restarts.
- **Usage is kept in a ledger, not re-read from transcripts.** `usage-ledger.ts` keeps `~/.chrome-workspaces/usage.json`: per transcript, its workspace, usage by model, day and hour, and the file's creation and modification times. `TranscriptTokens` counts only the live transcripts; the minute timer copies their figures in, and counts once, with a counter of its own, any other transcript written to since it was recorded (an archived workspace's, a session left by `/clear`, a resumed one) or that an archived workspace names and the ledger lacks. A transcript's entry is replaced each time, never added to, so resuming or restarting cannot count it twice, and the snapshot takes a transcript from the counter or the ledger, never both. After a restart a live transcript shows its ledger figures until its first count catches up. A fork copies the earlier conversation with its dates, so a message is left out when it is dated before its own file was created _and_ no later than the last message of a transcript of the same workspace created before it; either test alone is wrong (a restored file is created after its messages; a conversation picked up again after a fork goes past the fork's start). Days older than the trend's 60 are dropped and past days lose their hours, so the file stays around 100–200 KB. Entries outlive `history.json`'s 50, the 30-day session-file prune and claude's own transcript cleanup.
- **Plan limits come from the status line.** The same `--settings` file sets `statusLine` to `hooks/status-line.ts`, which saves `rate_limits` from claude's JSON to `~/.chrome-workspaces/plan-usage.json` (newest figure per window) and then runs the `statusLine` command from `~/.claude/settings.json` with the same stdin, so the status bar is unchanged. The helper reads that file for the Settings snapshot and drops a window once its `resets_at` has passed. No token or network call is involved; a project-level `statusLine` is replaced.
- **Status comes from hooks the helper adds itself.** Every workspace's `claude` starts with `--settings ~/.chrome-workspaces/hooks.json`, a file the helper rewrites at each start. It runs `hooks/session-state.ts` (plain TypeScript, run by `node` with type stripping, so Node 22.18+) on each of eleven events, and the script writes one status file per session to `~/.chrome-workspaces/sessions/`, and appends a line per event to `<session>.events.jsonl` beside it: the prompt, each tool call summarised (never its whole input), the `agent_type` claude sets on events inside a subagent (and `agent_id` where it sets one; the reducer nests by type, since the id is not always sent), the `subagent_type` of an Agent call, and compactions. The helper tails that file (last 512 KB) and folds it into turns; a panel whose Activity section is expanded is sent the turns again on every change to the sessions folder, through the same watcher that updates status. Both files are pruned together. Nothing is written to `~/.claude`, so the hooks touch only sessions the helper starts: a `claude` typed by hand after `exit` is not tracked, and `disableAllHooks` or a managed policy silences status. The hook always exits 0, files untouched for 30 days are pruned at startup, and the session files give status, `transcript_path` and a _static_ start `cwd`. Transcripts (`.jsonl`) carry per-message `cwd`, `timestamp`, `model`, `usage` and tool_use blocks. They are tail-read, and each message counts once (streaming repeats a message id). The worktree a session is in comes from the newest transcript `cwd`, not the session file. A session counts as a workspace's only if it started in the workspace's directory (or inside it, e.g. a worktree): a `claude` run from its shell in another project inherits the workspace id, and would otherwise be the one resumed and shown. The exception is a fork: when a workspace's transcript ends in a `continued-in` entry naming a session that was left out that way (up to five hops), the new session is the workspace's, so a `--fork-session` started from another workspace's shell still shows its status where the conversation lives. An ended session that never recorded a message is skipped too, so the last real conversation is the one resumed.
- **Shells inherit a scrubbed environment**: `CLAUDECODE` and `CLAUDE_*` are removed, otherwise `claude` thinks it is a child session and turns transcripts off.
- **Launch** is a login shell running `claude` (or the configured `claudeCommand`, falling back to `claude`), then `exec`ing the shell when it quits. The prompt travels through an env var, never the command text. Models, session ids, the command and configured repo names are validated before they reach a shell.
- **Paste and attach** use bracketed paste via `paste.ts`; dropped or pasted files are written to the uploads dir and their paths inserted.
- **A resumed session starts where claude was.** Claude moves into worktrees on its own, and its transcript records the directory on every message, but the session file's `cwd` stays where it started. When a workspace's terminal is started again (after a helper restart, say) with a conversation to resume, `launchDirectory()` in `launch-dir.ts` starts the shell in the transcript's last directory if it still exists and shares a git common directory with the workspace's own, else in the workspace's directory. `claude --resume <id>` finds a conversation from any worktree of the repository, so the transcript's folder does not matter. A new conversation always starts in the workspace's directory. **The transcript is looked for by session id.** The hook records the project folder of the directory claude started in, but claude files a conversation under the directory it is in, so a session that moved into a worktree (a `/quest` does) or was resumed from one can have its transcript in another project folder than `transcript_path` names. `locateTranscript()` in `session-status.ts` falls back to `<session id>.jsonl` in the other project folders (a miss is remembered for a minute); without it an ended session looked like one that never recorded a message and was skipped, so resume started a new conversation. Status, tokens, the activity timeline and "continued in" all use the located path.
- **Git runs with `GIT_OPTIONAL_LOCKS=0`**, validated paths and refs, and in the worktree Claude is in (`gitDirectory()` in `control/git-handlers.ts`). Worktrees are detected through `--git-common-dir`. Writes (stage, discard, commit, switch branch) are explicit requests.
- **Cost figures are estimates** from assumed per-family rates in `shared/usage/pricing.ts`, overridable under `pricing` in config. Unknown models show as unpriced rather than $0.
- **Replayed scrollback is flagged, and its answers dropped.** Attaching replays saved output into a fresh xterm; terminal queries in it (device attributes, say) would be answered again and typed into the shell as stray `1;2c` text. The helper marks the replay (`replay: true` on `output`) and the panel drops whatever xterm emits while parsing it.
- **The native-messaging host also starts the helper.** Settings cannot, because it talks to the helper and a stopped one is not listening. The host is launched by Chrome on demand, so a `start` request (`helper/src/platform/start-helper.ts`) bootstraps the launchd plist, or kickstarts the agent if it is loaded but not running. The panel's offline notice sends it.
- **A pop-out is a second view of a workspace's session.** `popout.html?ws=<id>` (`popout.ts`, opened by `popout-window.ts`; the address is built and parsed in `shared/workspaces/popout.ts`) attaches to `/attach?session=<id>` like the panel does, so it is pinned to that workspace and needs no selection. The helper already lets several clients attach to one session, so the panel and the pop-out both type into one PTY; the PTY has one size, so both send a `resize` when their window gains focus and the last view in use wins. The pop-out learns the workspace's name and status from `/control` state, and closes itself when the workspace leaves the list or the session sends `exit`.
- **The monitor and the plain terminal are sessions that are not workspaces.** The ids `monitor` and `shell` (`MONITOR_SESSION`, `SHELL_SESSION` in `shared/protocol/protocol.ts`) are attached like any workspace, and the helper starts `btop` (or `top`) or a login shell for them in `onUnknownSession`. `server.ts` ends the monitor when the last panel detaches; the shell keeps running until it exits. The panel's `tool-view.ts` has one xterm of its own that shows either, so neither touches the workspace selection or list. The shell has no `CW_WORKSPACE_ID`, so no status hooks apply to a `claude` typed in it.
- **Merge states are looked up 10 PRs per GraphQL query, two queries at a time** (`reviews.ts`): GitHub times out on big or many simultaneous queries. A failed batch is tried once more as two halves; a rate limit stops the remaining batches and pauses polling.
- **Restarting the helper ends every terminal**, including a Claude session running inside one. The restart is a detached `sleep N; launchctl kickstart -k`, so the reply gets out first.

## Data and config

Everything lives in `~/.chrome-workspaces/`: `config.json`, `token` (mode 0600, handed to the extension by a native-messaging host), `workspaces.json`, `history.json`, `usage.json`, `uploads/`, `helper.log` (copied to `helper.log.1` and emptied past 5 MB, checked at start and hourly). `CW_PORT` and `CW_DATA_DIR` run a second helper next to the real one. Config keys are documented in [configuration.md](configuration.md).

## Security model

The helper binds to `127.0.0.1`. WebSockets require the extension's `Origin` and the token; the HTTP API requires the token as a bearer header and rejects other origins. Markdown from PRs is parsed into DOM nodes, never injected as HTML. What reaches the network is listed in [privacy.md](privacy.md).
